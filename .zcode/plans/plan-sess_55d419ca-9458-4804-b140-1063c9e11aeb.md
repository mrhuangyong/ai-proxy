# 修复 `/failover` 参数不兼容 + 失败率过高

## 根因（已在代码中定位确认）

两个缺陷叠加导致"下游感觉立马失败"：

**缺陷 1 — 参数不兼容的 4xx 不触发轮换（"立马失败"的直接原因）**
`run_failover` 的失败判定（`handlers_failover.rs:270-272`）只认 `429/5xx/502`：
```rust
let is_failure = status == 429 || status.is_server_error() || status == 502;
```
当轮换到拒绝某个参数的模型时，上游回 **400/422**，内层 retry 会话判为 `SessionOutcome::Fatal` 直接返回（`retry_session.rs:282-289`），failover 循环看到 4xx **不在** `is_failure` 集合 → **不记失败、不 exclude、不试下一个 mapping**，400 原样透传给下游（line 362 `return response`）。更糟：sticky mapping 没被问责，下次请求还会命中它 → 反复瞬时失败。

**缺陷 2 — 无 per-route 参数清洗**
`handle_proxy_inner` 每次复用同一份客户端 IR，只换 `ir_request.model`（`handlers.rs:695-696`）。生成器按"字段是否存在"发参数，完全无视目标模型能力。唯一的清洗是 Kimi/Moonshot 的 `thinking` 硬编码 `base_url` 子串匹配。最大泄漏点：`extra` 透传——Completions parser 把所有未知 key 塞进 `extra`（`completions.rs:232-262`），四个生成器都**无过滤**注入（`completions.rs:214`、`anthropic.rs:238`、`gemini.rs:144`、`responses.rs:172`）。客户端的 `chat_template_kwargs`/`logit_bias` 等会原样落到错误的 provider body 里。

---

## 修复方案（DB 驱动能力系统 + 智能轮换不累计失败）

按你的选择：**DB 驱动能力系统（彻底）** + **轮换但不累计失败**。

### 设计原则
- **默认值宽松（全 1）** → 对现有配置**零回归**：未配置能力的模型行为完全不变。
- **failover 轮换修复独立生效** → 即使用户从不配置能力，参数 4xx 也会自动轮换到下一个 mapping（主疗效）。
- **能力清洗是可选优化** → 配置后主动剥离不兼容参数，省掉一次浪费的尝试。

### 改动 3 — 新建 `src-tauri/src/converter/sanitize.rs`（核心清洗函数）
```rust
pub struct ModelCapabilities { /* 与 DB 列一一对应 */ }

/// 在 handle_proxy_inner 里、生成上游 body 之前调用。
/// 按 caps 剥离/钳制 IR 中目标模型不支持的参数。
pub fn sanitize_ir_for_capabilities(ir: &mut IrRequest, caps: &ModelCapabilities) {
    if !caps.supports_thinking          { ir.thinking = None; }
    if !caps.supports_tools             { ir.tools = None; ir.tool_choice = None; }
    if !caps.supports_temperature       { ir.temperature = None; }
    if !caps.supports_top_p             { ir.top_p = None; }
    if !caps.supports_top_k             { ir.top_k = None; }
    if !caps.supports_presence_penalty  { ir.presence_penalty = None; }
    if !caps.supports_frequency_penalty { ir.frequency_penalty = None; }
    if !caps.supports_seed              { ir.seed = None; }
    if !caps.supports_response_format   { ir.response_format = None; }
    if !caps.supports_stream_options    { ir.stream_options = None; }
    if !caps.supports_stop              { ir.stop_sequences = None; }
    if let Some(cap) = caps.max_output_tokens {
        if let Some(mt) = ir.max_tokens { if mt > cap { ir.max_tokens = Some(cap); } }
    }
    if caps.extra_passthrough == 0 { ir.extra.clear(); }  // 堵住最大泄漏点
}
```
附 `#[cfg(test)]` 单元测试覆盖每个字段的剥离 + max_tokens 钳制 + extra 清空。

### 改动 6 — `handlers_failover.rs` 智能轮换（核心修复）
扩展失败判定 + 拆分"惩罚语义"：
```rust
let status = response.status();
let is_provider_failure = status == 429 || status.is_server_error() || status == 502;
let is_param_4xx = status.is_client_error() && status != StatusCode::UNAUTHORIZED
                   && status != StatusCode::FORBIDDEN; // 400/404/422/413/415 等

if is_provider_failure {
    // 真实 provider 故障：照常累计失败计数（可触达 threshold 打挂 mapping）
    VirtualRouter::record_failure(&resolved.mapping_id, threshold).await;
} else if is_param_4xx {
    // 参数/校验类：轮换但不累计（请求侧问题，不该惩罚 mapping）
    info!("[failover] param/4xx status={}, rotating without penalty", status);
    // 不调用 record_failure
}
if is_provider_failure || is_param_4xx {
    excluded.push(resolved.mapping_id.clone());
    last_response = Some(response);
    attempts += 1;
    continue;
}
```
- 401/403 不轮换（鉴权问题在同一 provider 的所有 mapping 上会重复，直接返回避免无谓重试；但下游仍能看到真实错误）。
- 额外小改进：扩充 `looks_like_error` 子串匹配（line 314-316），加入 `"invalid"`/`"unsupported"`/`"not support"` 等常见校验关键词，让 200-but-error 也更可靠地触发轮换。

## 不做什么（明确边界）
- **不在 mapping 切换之间加 sleep/backoff**：参数 4xx 是同步校验，加延迟无益；5xx 路径已有内层 retry 的指数退避。如后续观测到级联风暴再单独处理。
- **不改 `max_failover` 默认值（3）**：参数 4xx 轮换后通常 1-2 跳即成功。
- **不加 model 能力的自动探测**：纯手动配置，避免引入不可控的网络探测副作用。
- **不处理"流式首字节后失败无法轮换"**：这是架构性限制（stream 已 commit 给下游），本次不改；已有的 pre-first-token 内层 retry 是该路径的安全网。
